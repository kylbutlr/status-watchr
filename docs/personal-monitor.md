# Private Mac-to-iPhone monitor

## Scope and architecture

This implementation follows the owner's narrowed personal workflow, not the earlier public multi-provider product proposal. Start work normally in the Desktop App on this Mac, inspect its private activity feed on iPhone, and opt into persistent conversation watches. No remote execution, replies, or approval actions are exposed.

The path is:

1. The native observer selects conversation identity/title/project from `state_N.sqlite` and lifecycle identity/status/timestamps from `thread_history_N.sqlite`, read-only. For a recent completed turn, it can read the matching final agent answer from the local rollout and keep only a bounded preview. It checks known runs every five seconds and discovers up to 100 recent unarchived conversations every 15, 30, or 60 seconds. It checks up to 20 runs per conversation and recovers recent terminal runs from a ten-minute window.
2. Optional reviewed Codex hooks supplement lifecycle events and record approval attempts for local diagnostics. A hook does not prove that an approval is waiting for the owner because Codex may route it to Auto-review. A separate App Server is used only to inspect hook trust, not as the authority for Desktop activity. No thread is started or resumed. If that process fails, local metadata observation continues.
3. Normalized events enter an owner-only local outbox, then authenticated HTTPS ingestion. Database state and notification jobs are committed in one transaction. Source time governs state transitions; observation time cannot roll back a completed run.
4. A persistent conversation watch, not a one-shot run watch, selects future completion, failure, and available attention events. The optional temporary all-conversation setting adds coverage for current and newly observed conversations for 15 minutes, 1 hour, or 4 hours. It does not alter individual watches. Devices enrolled after an event and watches/windows enabled after an event do not receive historical alerts. The temporary setting was deployed with migration 005 on 2026-09-21; new-mode iPhone receipt remains pending.
5. Web Push sends fixed status copy, the watched conversation title, and an available final-reply preview to registered devices. Test alerts remain generic. The Home Screen app opens the authenticated dashboard. A scheduled Netlify function retries failed delivery and performs retention deletion.

The single-owner password session and ingest token remain private compatibility infrastructure. This is not a multi-user security model. Migration 004 adds watch preferences, push subscriptions, delivery records, and a single Mac-health record. Migration 005 adds one owner preference row, event source time on delivery jobs, and a shared SQL eligibility function rechecked before dispatch. No existing authentication scheme is replaced.

## Evidence and limits

The diagnostic on this Mac found a live in-progress turn and completed history. A separate App Server had reported the same Desktop conversation as `notLoaded`. The hook inventory reported six enabled but untrusted legacy Status Watchr hooks. These are current observations, not proof of every historical failure.

Codex's local SQLite schemas are implementation details, not a stable supported integration contract. The new reader fails unavailable when the selected schema cannot be read, rather than falling back to message bodies or guessing completion. An `inProgress` row cannot distinguish active work, waiting for input, or an abandoned run. The dashboard uses “In progress” and exposes source health separately.

The native hook installer preserves unrelated handlers, never changes the existing `notify` configuration, and never writes hook trust records. A `PermissionRequest` is no longer promoted to attention after a timer, even if no `PostToolUse` follows. Generic `waitingOnApproval` flags are also insufficient. Earlier hook-derived attention cached on disk is cleared when the updated observer starts. This prioritizes avoiding false “Needs you” alerts; real manual approvals can be missed until Codex provides an independently confirmed human-waiting signal. Question detection remains incomplete.

Question alerts are **disabled by default** in the local [question-alert trial](question-alert-trial.md). Accepted `request_user_input_async` tool hooks supply call identity and question count. A read-only SQLite expression selects only the corresponding identifiers and timestamps from explicit structured question-reply envelopes. Ordinary message text is not used to infer a question or answer, and question/answer contents are not returned to the observer. Native/hosted activation and end-to-end phone receipt remain pending. Automatic dismissal, blocking question tools, prose questions, and full manual approval coverage remain unverified. The optional final-reply preview is read only after a completed turn and is not interpreted as proof that the assignment succeeded. An interrupted run is not reported as a successful completion.

Exactly-once notification presentation cannot be guaranteed across a push-provider acknowledgement followed by a database failure. Job identity deduplicates repeated observations; stable push topics/tags reduce transport duplicates. Provider acceptance does not prove phone presentation. Focus, permissions, network availability, and expiry can prevent or delay an alert. Mute and device revocation remove pending jobs but cannot recall a push already in flight.

## Data boundary and retention

| Boundary | Data | Retention / deletion |
| --- | --- | --- |
| Codex databases and rollout | Explicit conversation identity, title, working-directory metadata; run identity, status, start/end timestamps; final answer for one recent completed turn | Read-only. The observer does not inspect approval contents, `item_json`, command text, or tool output. The rollout reader accepts only a validated path inside the Codex sessions directory and keeps only a bounded preview. Status Watchr never deletes Codex history. |
| Hook receiver | Codex sends full hook stdin over loopback, potentially including prompt/tool bodies. The receiver strips it to event, session, run, agent, and tool-name identifiers before callbacks or persistence. For an accepted async question only, it adds call ID and bounded question count. | Raw input is transient memory only; not logged or stored. 64 KiB limit, two-second connection timeout, loopback, POST/path/content-type and Origin checks. Other local processes are inside the trust boundary. |
| Local outbox | Normalized IDs, timestamps, status, approved conversation title, project label, and optional final-reply preview; no prompt/tool/terminal bodies, branch, or credentials | Atomic files with mode 0600 in `~/Library/Application Support/Status Watchr/outbox`, directory 0700. Removed after acceptance; seven-day expiry and 5,000-file cap. Failed delivery survives restart. Expiry runs when the observer processes the queue. |
| Local attention state | Conversation/run identifiers, random attention marker, tool name, request time | Owner-only `attention.json` beside the outbox. Earlier hook-derived entries are discarded when this candidate starts. The store has a seven-day maximum retention on load/save. No arguments or request content. |
| Hosted activity | Normalized lifecycle records, approved title, project label | Event rows deleted after 30 days of source age. Sessions deleted after 30 days without observation. A currently observed conversation's title can remain longer. The scheduled function must be deployed for deletion to occur. |
| Watches | Conversation ID, enabled flag, enable/update timestamps | Until owner changes it or explicitly deletes stored preferences. Muting removes pending jobs unless the temporary all-conversation window still covers them. |
| Temporary alerts | One owner row with window start/end timestamps | Off by default. Expiry is enforced by server time, without needing the browser. Latest timestamps remain until overwritten; turning off clears both timestamps. No new conversation content is collected. |
| Push subscriptions | Provider endpoint and browser encryption keys; device digest, enrollment time, test throttle timestamp | Until explicit device revocation or provider 404/410. Treat subscription URLs as credentials. Device listings return opaque IDs, never endpoints/keys. |
| Notification jobs | Opaque job ID, conversation ID, kind, device ID, event source time, attempts, lease/expiry/delivery times, and optional final-reply preview | Delivery expires after one hour; records deleted after seven days. The preview is cleared when the push provider accepts delivery. Temporary-only jobs are also denied after window expiry or cancellation. Provider TTL is at most one hour, shortened to remaining temporary coverage for temporary-only deliveries. At dispatch, the existing hosted title and bounded final-reply preview can enter the encrypted push payload. |
| Mac health | Source availability, hook trust state, last hook time, queued count, receipt time | One overwritten record. No machine name or filesystem path. |
| Browser | Auth cookie, refresh preference, opaque device registration ID; displayed signed-in activity in memory | Cookie expires after 30 days or logout. Device registration survives logout until revoked. No activity cache or offline service-worker cache is created. |

Titles and final-reply previews are explicit private-pilot exceptions and may contain client-sensitive text, including quoted code or secrets. Do not promise that the preview is non-sensitive. Project labels can also be identifying. The legacy command-line collector remains diagnostic/compatibility code and does not have the native observer's durability or readiness behavior.

There is no new export feature. An authenticated owner can retrieve the existing JSON session/timeline endpoints. Logs use fixed messages; do not log SQL exceptions, raw hooks, push errors, subscription endpoints, or credential values. Host/database backups, platform access logs, and provider retention are outside the application's deletion guarantees and need review before production acceptance.

## Threat model

- Stolen ingest token: permits forged activity and alert triggering, including a bounded displayed title and final-reply excerpt. It cannot read the dashboard, enroll devices, or execute commands. Rotate the server token and update the Mac Keychain to revoke it. This remains a shared single-device secret, not public device enrollment.
- Stolen owner session/password: can read titles/history, alter watches, and enroll or revoke notification devices. HTTPS, HttpOnly Secure SameSite=Strict cookies and same-origin JSON mutation checks apply. There is no tenant isolation, MFA, or new login rate limiter in this slice. Rotate password and session secret to invalidate sessions.
- Malicious subscription: an exact HTTPS push-host allowlist blocks using enrollment as an arbitrary outbound request proxy. Validate browser keys and cap device records. Subscription endpoints never appear in diagnostics.
- Malicious browser page targeting localhost: reject Origin-bearing hook requests and require the intended method/path and JSON type. The receiver does not execute hook content or return an approval decision. Local untrusted processes can still spoof loopback metadata.
- Network loss: native events remain queued; server delivery retries use leases and backoff. Old recovery events do not become new phone alerts. Queue and notification expiry intentionally bound retention and alert staleness.
- Lost/borrowed phone: revoke the device separately from logout. Logout does not mean push revocation. Watched conversation titles and final-reply previews may appear on the lock screen, in Notification Center, and on a paired watch. Configure iOS notification previews for the desired visibility.
- Observation failure: expose unknown/unavailable/stale source health. Do not equate a successful browser refresh with an operational Mac source.

## Setup after explicit deployment approval

The temporary-alert/mobile navigation update is local only. Apply the additive migration before deploying its web/functions bundle, following [the upgrade and rollback checklist](temporary-alerts.md). No native update or credential change is needed for this update.

1. Back up the private database, then apply [migration 004](../database/migrations/004_personal_notifications.sql) after migrations 001 through 003. It is additive, but deploying the retry function activates the documented retention deletions. This pilot's backup, restore verification, migration, and private web deployment are complete; see the [rollout record](pilot-rollout-2026-09-20.md) before repeating any setup step.
2. Generate a VAPID key pair using the installed `web-push` library in a secure local setup session. Store the public/private keys and owner-controlled contact subject as `WATCHR_VAPID_PUBLIC_KEY`, `WATCHR_VAPID_PRIVATE_KEY`, and `WATCHR_VAPID_SUBJECT` in the server environment. Do not paste private keys into chat or commit them. Existing database, password, session, and ingest secrets remain server-side.
3. Deploy the private web app and functions, including `notification-retry`. Verify the scheduled function is active on the production deployment, not merely in a preview. See [Netlify scheduled functions](https://docs.netlify.com/build/functions/scheduled-functions/).
4. Build a reviewed native artifact. Do not overwrite the installed application while it is running. Check bundle version monotonicity, signing identity, code signature, and notarization before an authorized installation or release. The existing release workflow also deploys production, so never use it for a local verification build.
5. Install the updated hook definitions only through an authorized companion setup. Review and trust their exact definitions using [Codex's documented hook review](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks). Never bypass trust. Keep the existing computer-use notify command intact.
6. On iPhone with iOS 16.4 or later, open the private site in Safari, sign in, use Share > Add to Home Screen, and open that installed app. Open Notification device settings, enable this device, then send a test. See [WebKit's Home Screen Web Push requirements](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).
7. Watch one conversation. Verify a real completion with the phone locked, the web app closed, and Wi-Fi off. Then verify repeated runs, mute, revocation, Mac network loss/recovery, failure, and available approval signals. The broader attention requirement cannot pass until real question and distinct-approval coverage is solved.

## Troubleshooting and distribution gate

- Dashboard works but Mac is not reporting: inspect native source health and local queue first. The public `/api/health` checks configuration flags, not database connectivity.
- Hooks installed but untrusted: installation is not execution. Review definitions; observe an actual lifecycle hook afterward. Do not troubleshoot an intentionally stopped app as a historical root cause.
- Notification settings unavailable: verify migration and server configuration. If the UI says push is unconfigured, watches can still be saved but no delivery will occur.
- Push test accepted but phone silent: verify Home Screen installation, permission, Focus, connectivity, and notification settings on the actual phone. An accepted request is not a delivered alert.
- Queue not draining: verify HTTPS URL, current ingest token, server health, and disk space. No error response body should be copied into public support output.

Keep this private. Public distribution still requires a supported source contract or documented compatibility policy, full attention coverage, stronger hosted identity/device controls, independent security review, signed/notarized native packaging, production backup/retention verification, and real phone delivery evidence.
